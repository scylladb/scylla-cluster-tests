# Hermes Support in SCT

Jira: [SCT-1330](https://scylladb.atlassian.net/browse/SCT-1330) (epic SCT-1418).

## 1. What Hermes Is

[Hermes](https://github.com/scylladb/scylla-hermes) is ScyllaDB's tool for live migrations
to ScyllaDB. Customers move production traffic through it.

### What it does

One `hermes` binary works in two modes:

- **Proxy.** It sits between the application and the clusters, and writes each request
  to the origin and to every target (one or more ScyllaDB clusters).
  - The origin is authoritative: the client gets the origin's reply.
  - A write that fails on a target goes to a failed-write log, to replay later.
- **CLI.** It prepares the targets, copies the data the proxy didn't see, and checks the result:
  - `create-schema` copies the schema from the origin to a target;
  - `migrate` copies the data written before the proxy started, while the proxy keeps
    writing the new data;
  - `replay-failed` replays the failed-write log;
  - validation compares every cell (bytes, write time, TTL) of origin and target,
    old and new data alike, and can check both ways. The exit code is the verdict.

The origin can be ScyllaDB, Cassandra or Astra. Targets are ScyllaDB only.

### How it differs from Gemini

Both work with more than one cluster in a run. Everything else differs:

| | Gemini | Hermes |
|---|---|---|
| What it is | A CQL client that generates random load and compares answers from two clusters | Data migration and verification from one cluster to one or more others, with a multi-target write proxy for live traffic |
| What it tests | Scylla correctness: the cluster under test against a reference cluster | A live migration: Hermes plus Scylla as the targets, under real load |
| Clusters | Two: the cluster under test and an oracle, the reference for correct answers | An origin, the source of truth, and one or more targets; the cluster under test is a target |
| Who writes to all clusters | Gemini itself | Hermes, as a proxy; the client sees one cluster |
| Workload | Random schemas and queries, generated by Gemini | Any CQL tool (latte first) |
| How it checks | Compares the query results of both clusters, during the run | Compares every cell (bytes, write time, TTL) of each target with the origin, both ways, after the copy |
| A mismatch means | A Scylla bug | Data lost or changed in the migration: a Hermes or Scylla bug |

So Hermes does not replace Gemini: it covers a different risk.

## 2. Problem Statement

Hermes's only real-cluster testing today is the authors' lab runs in
scylla-automation-framework (SAF).
Nothing runs it under SCT-scale load, for hours, with topology changes on the targets.

ScyllaDB already pins some of the database behaviours Hermes relies on
([scylladb/scylladb#33014](https://github.com/scylladb/scylladb/pull/33014)).
But no test checks the whole chain: client → Hermes → origin and target clusters → validation.
A Scylla regression that breaks a migration is found by a customer, not by us.

This plan adds that test: a migration run the way production runs it, with nemesis
on each cluster, and a verdict.

## 3. Current State

### SCT

- **More than one cluster in a run.** `db_type: mixed_scylla` adds an oracle cluster
  (`self.cs_db_cluster`) next to the cluster under test, created by
  `sdcm/tester.py:ClusterTester._create_oracle_cluster` on AWS, GCE, Azure and OCI.
  `db_type: mixed_cassandra` gives a Cassandra oracle, AWS only.
  A run has at most these two clusters today.
- **Tools in containers on loaders.** `sdcm/stress/base.py:DockerBasedStressThread` runs a tool image
  on a loader. The image comes from `stress_image.<tool>`, pinned in
  `defaults/docker_images/<tool>/values_<tool>.yaml`.
  `sdcm/gemini_thread.py:GeminiStressThread` is the closest example that uses two clusters.
- **Where a tool connects.** Each tool takes its contact node from
  `DockerBasedStressThread.db_node_to_query`.
  `sdcm/stress/latte_thread.py:LatteStressThread` is built on this base.
- **Registry access.** `sdcm/utils/docker_utils.py:docker_hub_login` logs loaders in to Docker Hub
  with `sdcm/keystore.py:KeyStore.get_docker_hub_credentials`.
  The KeyStore holds no other registry credential (no GHCR, no ECR).
- **Migration tests.** `spark_migrator_test.py:SparkMigratorTest` is the closest test shape:
  source cluster, target cluster, copy, then validation that fails the run.
  `platform_migration_test.py:PlatformMigrationTest` moves nodes between instance types
  in one cluster. It is not a data migration between clusters.
- **Nemesis on one cluster only.** `sdcm/nemesis/__init__.py:NemesisRunner` always disrupts
  `tester.db_cluster`, the cluster under test, and the nemesis options have no per-cluster form.
  Some nemesis code also reaches `tester.db_cluster` directly, for example to add or replace nodes.
- **No Hermes code** in SCT.

### Hermes

- **CLI still changing.** Its commands were renamed on 2026-11-26.
- **Client limits.** CQL protocol v4 only, no compression.
  Hermes sets its own write timestamps.
- **Data model limits.** No counters.
  LWT needs a Hermes option.
  No TTL on non-frozen collections.
- **Validation.** `--validate --validate-values` walks the origin's rows only, so a row that
  exists only on the target, such as one resurrected there, is never checked.
  A whole-table `--keys-from` entry is the two-way check: it also reports rows only the target has,
  and it runs while dual-write is on (`docs/migrations.md`, "The two-way check").
- **Production rollout** (`docs/migrations.md`, "Recommended rollout"): schema first, then dual-write,
  then `migrate` beside it with `--skip-errors` and `--retry-failed` until no range has failed,
  then validation and repair, then reads moved to a target (`read_from`), then cutover.
  The application keeps writing through all of it.
- **Schema on the targets.** Two ways, both built:
  - `create-schema --target <name>` copies keyspaces, types and tables from the origin.
    It runs before the proxy starts, and `migrate` refuses a table the target lacks.
    It needs the target's replication (`--replication`) and, for a new keyspace, `--tablets`.
    Tables are created on ICS whatever the origin uses; indexes and views are not created.
  - DDL sent through the proxy goes to the origin and every target (`allow_ddl: true`, the default).
    A target that misses it gets a failed-write record for `replay-failed`.
- **No distribution.** The repo is private and its license is proprietary.
  Releases have no files attached, and no image is published.
  The only build is a local one, `docker/compose/Dockerfile` → `scylla-hermes:local`.
  SAF builds Hermes from source by git ref.

## 4. Goals

**Main goal:** SCT runs a Hermes migration the way production runs it, with ScyllaDB
as the origin and the target, so a Scylla regression that breaks a migration fails an SCT run
before a customer meets it.

The end-to-end flow of a Hermes test:

1. Provision the origin and the targets.
2. Load the "old" data into the origin only, latte's schema with it.
3. Check that the origin's schema has nothing Hermes can't carry.
4. Copy the schema to each target with `create-schema`,
   with the replication and tablets setting of that target cluster.
5. Start Hermes on one of the test's loaders, next to the stress tools.
6. Start live load through Hermes. latte's `CREATE … IF NOT EXISTS` reaches every cluster
   and changes nothing. Start the nemesis threads of each DB cluster.
7. Copy the old data with `migrate --skip-errors`, then rerun it with `--retry-failed`
   until no range has failed.
8. Stop the nemeses, then replay failed writes.
9. Check each target against the origin both ways, values included.
10. Move the reads to the target, and keep the load running on it for a set time.
11. Stop the load. Report the verdict and the Hermes version to Argus.

The flow follows Hermes's recommended rollout: the live load runs from step 6 to step 11,
as an application keeps writing in production.
The overlap of old rows and live writes on the same keys is where a migration breaks.
Hermes's own scenarios 1.1 and 2.1 (`TEST_SCENARIOS.md`) copy with no live writes.
Production doesn't, so the plan doesn't either.
The test doesn't repair: after replay, any mismatch left is the bug to report.

Goals:

1. **Image** — SCT loaders pull a pinned Hermes image.
2. **Interface** — one Python module owns all Hermes logic (Phase 2).
   It takes an origin and a list of targets, so any number of targets works without changes to it.
   SCT config options, the test and the stress tools only call it.
   It doesn't depend on the cloud provider: it uses only the loader and the cluster objects.
3. **Proxy lifecycle** — the module starts Hermes and waits for its health check.
   At teardown it stops Hermes and collects its logs and its failed-write log.
4. **Load through Hermes** — `latte` connects to the endpoint the module gives.
   Another tool needs only its own driver settings to do the same.
5. **Verdict** — any mismatch the two-way check finds, or a non-zero exit,
   raises a `Critical` event.
6. **Pipeline** — one test case and one Jenkins job pass.
   A run with a planted mismatch fails.

The plan adds one SCT test, `hermes_test.py:HermesMigrationTest` (proposed name), in Phase 3.
It uses one target: the cluster under test, with the oracle cluster as the origin.
That is the most clusters SCT provisions in one run today.
Tests with more targets need SCT to provision more clusters; the module is ready for them.

Out of scope: stress tools other than latte, a Cassandra origin,
Hermes HA mode, Hermes's WAL, Alternator/DynamoDB.

## 5. Implementation Phases

### Phase 0 — Hermes image availability (BLOCKER, outside SCT)

**Importance:** Critical. Nothing in SCT can run Hermes without it.

SCT needs a versioned Hermes image that loaders can pull. None exists.

The blocker is a decision that hasn't been made: is the image private or public?
SCT works with either. The repository, its credentials and the build automation follow from it.

**0.1 Visibility.**
- Private: a repository the ScyllaDB org owns. This is not distribution, so the license allows it.
- Public: the license must allow it first (0.2). A public image can't be withdrawn:
  anyone can pull it, mirror it or cache it.
- Decision owner: the Hermes owner and product.
- SCT's design doesn't depend on the choice, only its credentials do (Phase 1).

**0.2 License (public image only).**
The Hermes `LICENSE` grants no right to distribute it "in source or binary form,
except under a written agreement with ScyllaDB".
The Hermes repo's own `docs/plans/open-source-practices.md` expects a public (Apache-2.0) release.

**0.3 Docker repository.**
- No Docker repository for Hermes exists.
- Proposed name: `scylladb/scylla-hermes`, the same as the GitHub repo.
- Choose the platform:

| Option | Push | Pull from SCT loaders | Needs |
|--------|------|-----------------------|-------|
| Docker Hub only | Organization Access Token from the org admin | Existing Docker Hub login, if that account can read private repos (Needs Investigation) | Org admin |
| GHCR and Docker Hub | GHCR: Hermes CI with the built-in `GITHUB_TOKEN`. Docker Hub: as above | Either one. GHCR needs a new KeyStore token with `read:packages` and a login step | Org admin for Docker Hub; GHCR works without one |

**0.4 Build automation (PR in scylla-hermes).**
- A tag builds the image for amd64 and arm64 on native runners and publishes one multi-arch tag,
  the same way latte's `docker.yml` does.
- The registry and the image name are inputs, so a later change of registry or visibility
  is a config change.
- Release binaries attached to GitHub releases are optional. SCT doesn't need them.

**Definition of Done:**
- [ ] Visibility decided, private or public, and recorded in this plan with who decided
- [ ] Platform chosen (Docker Hub only, or GHCR and Docker Hub), and `scylladb/scylla-hermes` exists there
- [ ] A tagged Hermes release publishes a multi-arch image

### Phase 2 — Hermes module and latte support

**Importance:** Critical. **Dependencies:** Phase 0, and Phase 1 when it applies.

The Python side of the integration: the Hermes module, and latte running through it.

**Hermes module.**
A new package, `sdcm/hermes/`, holds all Hermes logic.
Everything else in SCT uses Hermes only through it.
Its contract, filled in by Phases 2 and 3:

```python
class HermesMigration:
    def __init__(self, loader: BaseNode, origin: BaseCluster, targets: list[BaseCluster], image: str): ...

    # Phase 2
    def start(self) -> None: ...        # container up, health check passed
    def stop(self) -> None: ...         # graceful stop within the Hermes grace period
    @property
    def endpoint(self) -> str: ...      # host:port that CQL clients connect to
    def collect_logs(self, dest_dir: str) -> None: ...  # logs and failed-write log

    # Phase 3
    def create_schema(self, keyspaces: list[str]) -> None: ...  # on each target, before start()
    def migrate(self, keyspaces: list[str]) -> None: ...  # retries failed ranges until none is left
    def replay_failed(self) -> None: ...
    def validate(self, keyspaces: list[str]) -> HermesValidationResult: ...  # two-way, per target
    def read_from(self, target: BaseCluster | None) -> None: ...  # None: reads go to the origin
```

- `stress_image.hermes` pinned in `defaults/docker_images/hermes/values_hermes.yaml`.
- The module builds the Hermes config from the origin and each target:
  addresses, credentials, a name per target.
- Any Hermes error during the run becomes an SCT event.
- Hermes runs on a loader the stress tools also use. SCT's set of VMs stays as it is:
  no new node type and no extra loader for Hermes.
  The test case picks a loader instance type that fits Hermes and latte together.

**latte through Hermes.**
- When a test gives a `HermesMigration`, the stress-thread base connects to its endpoint
  instead of a DB node.
- Each tool declares the driver settings Hermes needs (protocol v4, no compression).
  A tool that doesn't declare them can't run through Hermes by mistake.
- latte is the only tool wired in this plan.
  Others (cassandra-stress, scylla-bench, …) are added later the same way.
- latte is always the latest release. The authors already run their load through Hermes
  with latte, so no compatibility work is expected.

**Integration test.**
Hermes with an origin and two target Scylla containers on the Docker backend,
to cover more than one target cheaply.
- If the image is private, the test is skipped when registry credentials are missing.
- Needs Investigation: `get_cluster_docker` has no oracle cluster today,
  so this may need its own fixture.

**Definition of Done:**
- [ ] The integration test pulls the pinned image, and Hermes becomes healthy
- [ ] The integration test runs a latte write workload and a latte mixed workload
  through Hermes to two targets, with no client errors
- [ ] `collect_logs` saves the Hermes logs and the failed-write log
- [ ] Unit tests: config generation with one and with two targets, the endpoint switch,
  and refusal of a tool without Hermes settings

### Phase 3 — Add test

**Importance:** Critical. **Dependencies:** Phase 2.

The SCT test, `hermes_test.py:HermesMigrationTest`, with its test case yaml (`mixed_scylla`).
It follows the flow in Goals. The module gets the rest of its contract:

- **Schema.** Before the proxy starts, the module reads the origin's `system_schema`
  and stops with an error on anything Hermes can't carry
  (counters, TTL on non-frozen collections).
  SCT can't read this from the workload: latte's schema lives in its rune script.
  Then it runs `create-schema` for each target, with that target cluster's datacenters,
  replication factor and tablets setting taken from SCT.
- **Copy.** While the live load runs, the module runs `migrate` for the pre-loaded data,
  as Hermes's rollout asks for a copy beside live writes:
  - source write times kept (the default), and `--collection-anchor-timestamp`
    set to the time the proxy started;
  - `--skip-errors`, then `--retry-failed` until no range has failed,
    so a node down on either cluster doesn't stop the copy.
- **Verdict.** After the nemeses stop, the module runs `replay-failed`,
  then the two-way check with values for each target, with the live load still running.
  A non-zero exit or a reported mismatch on any target raises a `Critical` event.
  The mismatch count per target and the Hermes version go to Argus.
- **Read switch.** The module moves the reads to the target live, as production does:
  it edits `read_from` and reloads Hermes, so connected clients follow with no restart.
  The load keeps running for a set time. Client errors fail the run.
- **Config options.** The test case turns Hermes on, picks its loader and overrides parts
  of its config through SCT options.
  They hold no Hermes logic. Defaults keep every existing test unchanged.
- **Job and docs.** `test_metadata` for the test case, a Jenkins job for it,
  and `docs/hermes.md`: what the test checks, how to run it, how to bump the Hermes version.

#### Nemesis on each DB cluster

Each DB cluster gets its own nemesis threads, set in the test config only.
A cluster with no nemesis settings gets none, so the origin, the target or both can be disrupted.

- `NemesisRunner` takes the cluster it disrupts. The default stays the cluster under test,
  so existing tests don't change.
- The test adds a nemesis set to each DB cluster. Each cluster starts and stops its own threads.
- Nemesis code that reaches `tester.db_cluster` directly uses the runner's cluster instead.
- Events and Argus name the cluster of each disruption.
- Needs Investigation: the node allocator shared by all runners (`tester.nemesis_allocator`),
  and new nodes for the oracle cluster, which have their own instance type.

The nemesis options get an `_oracle` form, like `instance_type_db_oracle`:

```yaml
nemesis_class_name: SisyphusMonkey            # the cluster under test: the target
nemesis_selector: >-
  StopStartMonkey or ScyllaKillMonkey or HardRebootNodeMonkey or StopWaitStartMonkey
  or ClusterRollingRestart or BlockNetworkMonkey
  or NodeTerminateAndReplace or GrowShrinkClusterNemesis or DecommissionMonkey
  or TerminateAndRemoveNodeMonkey or SplitMergeTabletsWithAlter
  or MajorCompactionMonkey or RestartThenRepairNodeMonkey
nemesis_class_name_oracle: SisyphusMonkey     # the oracle cluster: the origin
nemesis_selector_oracle: >-
  StopStartMonkey or ScyllaKillMonkey or ClusterRollingRestart or BlockNetworkMonkey
```

Each group comes from a production case in the Hermes docs:

| Group | Clusters | Nemeses | Production case in the Hermes docs |
|-------|----------|---------|------------------------------------|
| Node down | origin, target | `StopStartMonkey`, `ScyllaKillMonkey`, `HardRebootNodeMonkey`, `StopWaitStartMonkey` (target only) | A target node down under load, then replay; `migrate` through a source node restart (`real-cluster-tests.md`, `TEST_SCENARIOS.md` 2.3) |
| Rolling restart | origin, target | `ClusterRollingRestart` | A rolling upgrade; a rolling restart during `migrate` (`error-handling.md`, `real-cluster-tests.md`) |
| Network loss | origin, target | `BlockNetworkMonkey` (needs `extra_network_interface: true`) | A network partition between the proxy and a cluster; real packet loss (`error-handling.md`, `real-cluster-tests.md`) |
| Node replace and bootstrap | target | `NodeTerminateAndReplace`, `GrowShrinkClusterNemesis`, `DecommissionMonkey`, `TerminateAndRemoveNodeMonkey` | A target node replaced; a target busy bootstrapping (`error-handling.md`) |
| Tablet moves | target | `SplitMergeTabletsWithAlter` (tablets only) | Tablet migration during traffic (`real-cluster-tests.md`) |
| Compaction and repair | target | `MajorCompactionMonkey`, `RestartThenRepairNodeMonkey` | A target busy with compaction or repair (`error-handling.md`) |

A nemesis that doesn't apply skips itself: `BlockNetworkMonkey` without
`extra_network_interface`, `SplitMergeTabletsWithAlter` without tablets.

Everything else is left out. Most of it matches no production case in the Hermes docs.
These would fail the run with a false mismatch, because they change one cluster alone:
- deletes and truncates (the `delete_rows` flag);
- schema and table-property changes (the `schema_changes` and `modify_table` flags),
  such as a dropped column or a new default TTL;
- data loaded straight into one cluster: `RefreshMonkey`, `RefreshBigMonkey`,
  `LoadAndStreamMonkey`, `MgmtRestore`.

**Definition of Done:**
- [ ] A clean run reports zero mismatches
- [ ] `migrate` finishes while the live load is still running
- [ ] A value changed and a row added straight on the target, in rows the load doesn't touch,
  each make the run fail
- [ ] Each nemesis of both lists runs at least once in the job, on its own cluster,
  with a clean verdict
- [ ] Reads moved to the target run for the set time with no client errors
- [ ] Unit tests: a runner given the oracle cluster disrupts only its nodes, and a config
  without `_oracle` nemesis options starts no thread on the oracle
- [ ] `create-schema` makes every table of the origin's keyspace on each target
- [ ] A schema with a counter table stops the run before the proxy starts
- [ ] Options documented, and `docs/configuration_options.md` regenerated
- [ ] The job passes in staging, and `docs/hermes.md` is listed in `docs/INDEX.md`
- [ ] Unit tests map exit codes and output to events, and cover the option defaults

## 6. Testing Requirements

- **Unit (`unit_tests/`)**: config generation for one and for several targets,
  the stress-tool endpoint switch, the schema check, the registry login,
  the mapping from exit code and output to events, the option defaults,
  and nemesis threads per cluster.
- **Integration**: the Phase 2 test, on the Docker backend.
- **Provision**: provision test labels on the Phase 2 PR, because log collection changes.
- **Manual / staging**: the Phase 3 job.

## 7. Success Criteria

All Definition of Done items above, plus:

- The Phase 3 job passes three runs in a row, so a red run means a bug, not a flaky test.

## 8. Risk Mitigation

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| The visibility decision takes weeks | Medium | No SCT phase can start: the image is a hard blocker | The decision is requested from its owners when this plan is approved, with a due date in the epic |
| Image pushed as public by mistake while the decision is private | Low | Proprietary binary is out and can't be withdrawn | The repository is created private; the workflow doesn't change its visibility |
| A nemesis hits the cluster under test while set for the oracle | Medium | The origin is never disrupted, and the target gets twice the disruption | Unit tests per listed nemesis; the origin list starts with four nemeses only |
| The check under live load reports a row a live write just changed | Low | A red run that isn't a bug | The two-way check reads a row on the origin again before it reports it; a run that shows the race goes to the Hermes authors |
| Hermes CLI keeps changing | High | SCT commands break on a version bump | Pin the image tag; only the Hermes module calls the CLI, so a bump changes one place |
| Hermes limits look like Scylla bugs | Medium | False failures, lost trust | The schema check stops the run before the proxy starts; failures are triaged against Hermes limits first |
| Cassandra origin needed sooner | Low | `mixed_cassandra` is AWS-only | Depends on [Cassandra Cluster Support](../infrastructure/cassandra-cluster-support.md) |
