# Nemesis High Disk Utilization Support

## 1. Problem Statement

The 90%-disk elasticity test (`test-cases/features/elasticity/elasticity-90-percent-with-nemesis.yaml`)
selects nemesis with `nemesis_selector: 'supports_high_disk_utilization'`. Today **15 nemesis are
excluded** because they carry `supports_high_disk_utilization = False`. This shrinks chaos coverage
under the high-disk condition — the exact regime where ScyllaDB is most fragile (compaction, streaming,
and ENOSPC handling). Several exclusions are conservative or implementation-driven rather than
fundamental, so real bugs in those operations at 90% disk go untested.

Measurable pain points:
- 15 of the disruptions are unavailable at 90% disk (≈ the entire topology-shrink, MV/SI, backup, and
  scrub families).
- The flag was applied largely as a blanket "consumes disk → off" with terse one-line comments; no
  systematic analysis distinguishes *inherent* limits from *fixable* ones.
- The four Manager backup exclusions rest on a factual error: a snapshot hard-links SSTables rather than
  copying them, so it consumes no space of its own. The real defect is that the snapshot is never deleted.
- Two exclusions (`#22088`) mask an open **ScyllaDB bug** and are the only fundamentally blocked cases.

`StartStopValidationCompaction` and `CorruptThenScrubMonkey` remain **permanently excluded** while
[scylladb/scylladb#22088](https://github.com/scylladb/scylladb/issues/22088) is open. They are the only
disruption family that keeps no high-disk coverage at all.

Reference: `GrowShrinkClusterNemesis` (`monkey/__init__.py:42`) is already supported because it grows
before shrinking — the proof-of-concept for the grow-first fix. `DecommissionStreamingErrMonkey`
(`monkey/__init__.py:633`) carries no flag at all, so it defaults to `True` and already runs at high disk.

**Capacity reasoning (why grow-first works for the topology-shrink family):**
Cluster of `n` nodes at ~90%, dataset `D`, RF `r` → per-node `≈ D·r/n`. **Shrink-first** (current):
node dies → `removenode` rebuilds its replicas onto `n-1` survivors → `D·r/(n-1) > 90%` → ENOSPC.
**Grow-first** (proposed): add a node → existing nodes stream out to it (usage drops) → then
terminate + `removenode` → back to `n` live nodes at `D·r/n` ≈ the steady 90% the cluster already
sustains. Safe.

**Why backup is not a capacity problem:** a Manager backup takes a snapshot, which hard-links SSTables
into `snapshots/`. No data is duplicated. The only effect is that compaction cannot reclaim the pinned
SSTables while the snapshot exists. Deleting the snapshot when the nemesis finishes is therefore the
complete fix — no free-space guard and no keyspace scoping are needed. See Phase 4 for the current gap.

## 3. Goals

1. **Every disruption family gains high-disk coverage** except the `#22088`-blocked scrub/validation family.
   Note this is deliberately *not* stated as "reduce the excluded count to N" — the topology-shrink family
   keeps its shrink-first classes excluded on purpose (Goal 2), so the raw count is not the right metric.
2. Cover the topology-shrink family at 90% by adding **grow-first sibling classes** flagged
   `supports_high_disk_utilization = True`, while the existing shrink-first classes keep the flag `False`.
   Degraded-cluster `removenode`/decommission coverage in normal longevity is preserved unchanged.
3. Enable MV/SI nemesis (`CreateIndexNemesis`, `AddRemoveMvNemesis`, `KillMVBuildingCoordinator`) by
   operating on a dedicated, row-bounded table whose index/MV fits within free headroom.
4. Enable Manager backup nemesis (`MgmtBackup`, `MgmtBackupSpecificKeyspaces`, `ManagerRcloneBackup`,
   `ManagerNativeBackup`) by deleting the snapshot reliably, including when the backup task fails.
5. Make `MgmtRestore` size the restored snapshot to *actual current free space*, or document it as
   inherent and keep it off.
6. No node exceeds ~95% disk on the elasticity-90 run for any newly-enabled disruption.

## 4. Implementation Phases

> **No runtime disk-usage checks anywhere.** Every behavior below is fixed at class-definition time, so a
> given nemesis behaves identically on every run. Where high disk needs different behavior from normal
> longevity, that is expressed as a **separate sibling class** with its own flag value (Phases 1–2), never
> as a measured branch inside a shared disrupt method. This keeps selection deterministic and reviewable
> from `data_dir/nemesis.yml` alone.

Every phase carries these two shared DoD items, since regeneration is pre-commit enforced and each flag
change needs its own validation:

- `./sct.py create-nemesis-yaml` and `./sct.py create-nemesis-pipelines` re-run, generated files committed,
  `uv run sct.py pre-commit` clean.
- elasticity-90 run completes with peak `node_filesystem` usage under 95% during the newly-enabled
  disruption (reuse the Prometheus query pattern in `longevity_oos_test.py:_query_disk_usage`).

### Phase 1 — Grow-first sibling classes for the `removenode` family (Importance: High)
- Add an `add_new_node_first: bool = False` parameter to `_remove_node_add_node` (`__init__.py:3546`): when
  set, add and bootstrap the replacement node and wait for `NORMAL` +
  `wait_no_tablets_migration_running` *before* terminating the target and running `removenode`. The
  capacity reasoning in Section 2 is the justification.
- Add runner entry points that pass `add_new_node_first=True`, wrapping
  `disrupt_remove_node_then_add_node` (`__init__.py:3521`) and the
  `_refuse_connection_from_banned_node` finalizer (`__init__.py:4973`).
- Add three sibling classes carrying `supports_high_disk_utilization = True`, copying the flags and
  decorators of their originals (`disruptive`, `topology_changes`, `kubernetes = False` for the
  `removenode` one, `@target_all_nodes` for the two isolate ones):

  | New class | Sibling of | Flag |
  |---|---|---|
  | `GrowThenRemoveNodeMonkey` | `TerminateAndRemoveNodeMonkey` (`:601`) | `True` |
  | `GrowThenIsolateNodeWithProcessSignalNemesis` | `IsolateNodeWithProcessSignalNemesis` (`:791`) | `True` |
  | `GrowThenIsolateNodeWithIptableRuleNemesis` | `IsolateNodeWithIptableRuleNemesis` (`:801`) | `True` |

- The three original classes keep `supports_high_disk_utilization = False`. Update their inline comments to
  say *why* they stay off and point at the sibling, so the pairing is discoverable.
- The `_refuse_connection_from_banned_node` path reaches `removenode` with a node that is already
  isolated/banned — adding a new node while another is banned needs explicit verification, not just the
  straightforward `disrupt_remove_node_then_add_node` path.
- **Dependencies:** none.
- **Deliverables:** `add_new_node_first` path; two runner entry points; three sibling classes; three
  regenerated pipelines.
- **DoD:** the three new classes are selected by `nemesis_selector: 'supports_high_disk_utilization'` and
  the three originals are not, both covered by a registry-selection unit test; no node exceeds ~95% during
  the disruption; normal longevity still runs the original shrink-first classes unchanged; + the two
  shared items.

### Phase 2 — Grow-first sibling classes for the decommission family (Importance: Medium)
- Same pattern: add `GrowThenDecommissionMonkey` and `GrowThenDecommissionSeedNode` with the flag `True`,
  reordering `disrupt_nodetool_decommission` / `disrupt_nodetool_seed_decommission`
  (`__init__.py:1358`/`1330`) to add before removing. The originals keep `False`.
- **Open question:** overlap with `GrowShrinkClusterNemesis` semantics — confirm value vs. just relying on
  GrowShrink for topology coverage at high disk. Two new classes means two new Jenkins pipelines, so this
  may well be dropped as redundant; record the decision either way.
- **Dependencies:** Phase 1 (reuses the `add_new_node_first` mechanism).
- **DoD:** decision recorded; if implemented, two sibling classes + the two shared items.

### Phase 3 — Bounded dedicated table for MV/SI nemesis (Importance: High)
- Add a helper that creates a small dedicated keyspace/table with a capped row count (sized so the
  resulting SI/MV fits comfortably in free headroom at 90%), used by `disrupt_create_index`
  (`__init__.py:4531`), `disrupt_add_remove_mv` (`__init__.py:4590`), and
  `disrupt_kill_mv_building_coordinator` (`__init__.py:5089`). `KillMVBuildingCoordinator` needs a
  tablets-enabled dedicated table.
- Drop both the table and the view/index at the end, **including when the disruption fails**.
- Unlike Phases 1–2 this changes the existing classes in place rather than adding siblings, because the
  disruption being exercised (build an MV/SI, then drop it) is the same either way — only the base table
  size differs. **Trade-off, accepted:** normal longevity loses its full-size MV/SI build. Size the
  bounded table as large as free headroom at 90% allows, so it is the largest MV that fits rather than an
  arbitrarily small one.
- Flip flags to `True`: `monkey/__init__.py:707`, `:718`, `:814`.
- **Dependencies:** none.
- **DoD:** three flags flipped; elasticity-90 build+drop cycle stays within free space; no dedicated
  keyspace or view survives a failed disruption; + the two shared items.

### Phase 4 — Reliable Manager backup snapshot deletion (Importance: Medium)

The snapshot pins SSTables but duplicates nothing, so the fix is deletion, not a guard. Today that
deletion is missing or unreliable:

- `_mgmt_backup` (`__init__.py:3134`) **never deletes its own snapshot.** `_delete_existing_backups`
  (`__init__.py:3119`) is called at `__init__.py:3154`, *before* the backup starts, and only reaps
  leftovers from previous runs. So `MgmtBackup` and `MgmtBackupSpecificKeyspaces` leave their snapshot
  pinning SSTables indefinitely.
- The failure paths at `__init__.py:3179` (`ERROR`/`ERROR_FINAL`) and `__init__.py:3182` (timeout)
  `assert False` and bail out with the snapshot still in place.
- `disrupt_manager_backup` (`__init__.py:2923`) *does* delete at `__init__.py:2936`, but not in a
  `finally`, so it leaks the snapshot whenever `_manager_backup_and_report` raises.

Scope:
- Delete the snapshot in `_mgmt_backup` in a `finally` covering the DONE, ERROR and timeout paths.
- Move `disrupt_manager_backup`'s existing `delete_backup_snapshot()` into a `finally` for the same reason.
- Flip flags to `True`: `monkey/__init__.py:374` (`MgmtBackup`), `:385` (`MgmtBackupSpecificKeyspaces`),
  `monkey/runners.py:120`, `:129`. Correct their misleading
  `# Snapshot/Restore operations consume disk space` comments.
- **Dependencies:** none.
- **DoD:** no snapshot survives any of the four nemesis, including on backup error or timeout; elasticity-90
  shows disk usage returning to its pre-disruption level after each backup nemesis; + the two shared items.

### Phase 5 — MgmtRestore sizing to free headroom (Importance: Low)
- Unlike backup, restore genuinely adds data, so this is a real capacity concern rather than a mislabelled
  one. `choose_snapshot` in `disrupt_mgmt_restore` (`__init__.py:2947`) caps snapshots via
  `total_partition_size / size >= 20`, but `get_total_scylla_partition_size` (`__init__.py:2948`) reads
  `df` field `[1]` — the partition's *total* size, not what is free. At 90% utilization that cap is roughly
  10x too permissive.
- Bound selection against `df` field `[3]` (available) instead. If no bound is feasibly safe at 90%,
  document as inherent and keep the flag `False`.
- **Dependencies:** none.
- **DoD:** either the flag is flipped with a validating elasticity-90 run + the two shared items, or the
  limitation is documented in `docs/nemesis.md` with the capacity reasoning. Either way the existing
  "There's not enough space for any snapshot restoration" assertion must still fire cleanly rather than
  selecting an oversized snapshot.

## 5. Testing Requirements
- **Unit:** registry selection under `nemesis_selector: 'supports_high_disk_utilization'` includes the new
  grow-first siblings and the newly-flipped classes, and still *excludes* the shrink-first originals;
  generator output matches committed `nemesis.yml`. Use `FakeRemoter`/mocks per `writing-unit-tests`.
- **Integration/manual:** run `elasticity-90-percent-with-nemesis.yaml` (or a BYO equivalent) per phase;
  assert peak `node_filesystem` usage stays < 95% during each newly-enabled disruption (reuse the
  Prometheus query pattern in `longevity_oos_test.py:_query_disk_usage`).
- **Regression:** confirm normal longevity still exercises the original shrink-first remove-then-add and
  decommission classes with unchanged behavior — the sibling approach means this must be a true no-op for
  them.
- **Failure-path:** for Phase 4, force a backup task error and a timeout and assert no snapshot remains.
  For Phase 3, force a failure mid-MV-build and assert the dedicated keyspace is gone.

## 6. Success Criteria
- All Phase DoD items checked.
- Every disruption family except the `#22088`-blocked scrub/validation family has at least one class
  selectable under `nemesis_selector: 'supports_high_disk_utilization'`, per Goal 1.
- No ENOSPC-induced node shutdown attributable to a newly-enabled nemesis on the elasticity-90 run.
- Normal longevity behavior is unchanged for the shrink-first topology classes.
- `data_dir/nemesis.yml` and pipelines regenerated and consistent; `uv run sct.py pre-commit` clean.
- `docs/nemesis.md` and the `writing-nemesis` skill flag table document the sibling-pair convention and the
  new flag values.

## 7. Risk Mitigation
| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Sibling classes add generated Jenkins pipelines and `nemesis.yml` entries (3 from Phase 1, 2 more from Phase 2) | High | Low | Accepted cost of preserving both orderings. Phase 2 is explicitly droppable if `GrowShrinkClusterNemesis` already covers it, which caps the growth at 3 |
| Sibling and original drift apart over time (a fix applied to one, not the other) | Med | Med | Siblings delegate to the same `_remove_node_add_node` with only `add_new_node_first` differing, so there is one implementation and no duplicated disrupt logic. Cross-reference the pair in both inline comments |
| Bounded MV/SI table reduces realism of the disruption everywhere, not just at high disk | High | Med | **Accepted trade-off** (Phase 3) — the MV/SI disruption is the same operation either way. Size the bounded table to the largest MV that fits in free headroom at 90% |
| Backup snapshot leaks on the failure path and keeps pinning SSTables | Med | High | `finally`-based deletion in both `_mgmt_backup` and `disrupt_manager_backup`; failure-path test asserting no snapshot remains |
| Grow-first while a node is already banned/isolated behaves unexpectedly in the `IsolateNode*` finalizer | Med | Med | Phase 1 explicitly verifies the `_refuse_connection_from_banned_node` path, not only `disrupt_remove_node_then_add_node` |
| Forgetting to regenerate `nemesis.yml`/pipelines | Med | Low | Pre-commit hooks fail the build on drift; also a shared DoD item on every phase |
| Tablets vs vnodes behavior differences in grow-first timing | Med | Med | Wait for `NORMAL` + `wait_no_tablets_migration_running` before shrink; validate on tablets config |
