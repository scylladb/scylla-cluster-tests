# Mini-Plan: FixedOrderMonkey Nemesis Runner

**Date:** 2026-09-15
**Estimated LOC:** ~120

## Problem

Every existing multi-nemesis runner shuffles its disruption list, so a reproduction
scenario that depends on a specific disruption sequence cannot be expressed. Reproducing a
known bug ("decommission, then repair, then enospc") today needs a bespoke runner class or
a lucky `nemesis_seed`. A runner that executes an explicitly configured order, then repeats
that order for the rest of the test, covers this without new code per scenario.

## Approach

- Add a `nemesis_fixed_order` config option holding an ordered list of nemesis class names.
  It is consumed only by the new runner; other runners ignore it.
- Add `FixedOrderMonkey` to `sdcm/nemesis/monkey/runners.py`. It resolves the configured
  names against the nemesis registry itself, instantiating one nemesis per distinct name
  and placing an entry per occurrence in the configured order, so a name may repeat. An
  unknown name raises and the message names it.
- Resolve names directly rather than through `build_disruptions_by_name`. That helper exists
  to apply `nemesis_selector` and composes an `"A or B"` phrase which
  `build_disruptions_by_selector` then parses as an AST and evaluates against every
  subclass, only to recover names the caller already had. This runner takes an explicit
  list, so it needs neither the selector nor the phrase, and staying off that helper keeps
  its seven existing callers untouched.
- Skip the selector entirely, including the implicit `and kubernetes` gate that
  `build_disruptions_by_selector` applies on k8s backends. A listed nemesis that cannot run
  on the current backend therefore reaches `precheck_nemesis`, which prunes it and reports
  a SKIPPED event to Argus, or raises `UnsupportedNemesis`, which `run()` already catches
  and logs. For an explicitly typed sequence a reported skip beats a silent drop during
  discovery.
- Repetition needs no new code: `NemesisRunner.call_next_nemesis` already walks
  `infinite_cycle`, an `itertools.cycle` over `disruptions_list`, so the list restarts from
  the first entry once exhausted.
- Log the resolved sequence at INFO, so the order actually executed is visible in the test
  log after precheck pruning.
- Ignore `nemesis_multiply_factor` — "fixed order" means the configured sequence and
  nothing else. Log that the factor is not applied when it is set above 1.
- Validate at config-load time in `sdcm/sct_config/config.py`: `nemesis_fixed_order` must be
  non-empty when `FixedOrderMonkey` appears in `nemesis_class_name`, and must be unset
  otherwise, so a typo in the runner name fails before the cluster is provisioned.
- One `nemesis_fixed_order` list is shared by every `FixedOrderMonkey` thread, unlike
  `nemesis_selector` and `nemesis_seed`, which map per thread. Per-thread orders are out of
  scope.
- Flow end to end: config validated -> runner constructed -> names resolved to nemesis
  instances in configured order -> `precheck_nemesis` prunes infeasible entries (order of
  the survivors is kept) -> run loop cycles the surviving list until the test ends.
