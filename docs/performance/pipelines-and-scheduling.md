# Pipelines and Scheduling

Which perf job runs, when, where, and against which version.

---

## 1. Layers

```
configurations/triggers/perf-regression.yaml      <- single source of truth (edit this)
                |
                |  pre-commit hook: generate-trigger-jenkinsfiles
                v
jenkins-pipelines/master-triggers/sct_triggers/perf-regression-trigger.jenkinsfile  (GENERATED)
                |
                |  triggerMatrixPipeline (vars/triggerMatrixPipeline.groovy)
                v
jenkins-pipelines/performance/branch-perf-v17/.../<job>.jenkinsfile
                |
                |  perfRegressionParallelPipeline (vars/perfRegressionParallelPipeline.groovy)
                v
hydra run-test <test_name> --backend <backend>     (one parallel stage per sub-test)
```

> **Do not hand-edit `perf-regression-trigger.jenkinsfile`.** It is generated by
> `python3 utils/build_system/generate_trigger_jenkinsfiles.py`, wired as the
> `generate-trigger-jenkinsfiles` pre-commit hook on `^configurations/triggers/.*\.yaml$`.

## 2. The trigger matrix — `configurations/triggers/perf-regression.yaml`

Replaces the legacy `testRegionMatrix` in `vars/perfRegressionParallelPipelinebyRegion.groovy`.
Four top-level sections:

### `jenkinsfiles:`
Which generated file this YAML produces.

### `cron_triggers:`
Each entry is a schedule plus the params handed to the trigger job. `{branch}` is templated.

| Schedule | `labels_selector` | Owner |
|---|---|---|
| `0 8 * * *` (daily 08:00) | `alternator-daily` | radoslawcybulski |
| `0 8 * * 6` (Sat 08:00) | `alternator-weekly` | radoslawcybulski |
| `00 6 */14 * *` (every 14 days) | `master-2weeks` | juliayakovlev |
| `0 23 */21 * *` (every 21 days) | `master-3weeks` | juliayakovlev |
| `0 6 1 * *` (1st of month) | `master-monthly` | juliayakovlev |
| `13 6 8-14 * 2` (2nd Tuesday) | `gce-custom-monthly` | valerii.ponomarov |

### `version_resolution: "common"`
All jobs in one triggered run get the newest build published across **every**
backend/region/arch in the matrix, rather than each backend picking up whatever nightly it
happens to have. The YAML states the reason inline:

> *Performance numbers are only comparable when every job of a run measures the same build.*

### `defaults:`
Applied to every job entry: `provision_type: on_demand`, `post_behavior_*: destroy`,
`use_job_throttling: true`, `billing_project: "weekly performance regression"`.

### `jobs:`
One entry per (job, version-tier) combination. Keys:

| Key | Meaning |
|---|---|
| `job_name` | Fully-qualified Jenkins path, leading `/` |
| `backend` | `aws`, `gce`, `azure`, ... |
| `arch` | `x86_64` (default) or `aarch64` |
| `include_versions` / `exclude_versions` | Mutually exclusive version gating |
| `labels` | Which `labels_selector` cron fires this entry |
| `job_throttle_category` | Concurrency group, e.g. `SCT-perf-eu-west-2-i8g` |
| `params.region` | Region for this entry |
| `params.sub_tests` | JSON-encoded list of test method names |

Example — the same job appears twice, once for `master` on a monthly label, once for release
branches with no label and a reduced sub-test list:

```yaml
- job_name: "/scylla-enterprise/perf-regression/scylla-enterprise-perf-regression-predefined-throughput-steps-i8g-vnodes"
  backend: "aws"
  arch: "aarch64"
  include_versions: ["master"]
  labels: ["master-monthly"]
  job_throttle_category: "SCT-perf-eu-west-2-i8g"
  params:
    region: "eu-west-2"
    sub_tests: '["test_read_gradual_increase_load", "test_mixed_gradual_increase_load", "test_write_gradual_increase_load", "test_read_disk_only_gradual_increase_load"]'

- job_name: "/scylla-enterprise/perf-regression/scylla-enterprise-perf-regression-predefined-throughput-steps-i8g-vnodes"
  backend: "aws"
  arch: "aarch64"
  exclude_versions: ["2025.2", "2025.1", "2024.2", "2024.1", "master"]
  labels: []
  job_throttle_category: "SCT-perf-eu-west-2-i8g"
  params:
    region: "eu-west-2"
    sub_tests: '["test_mixed_gradual_increase_load"]'
```

### Selection semantics

1. **Version gating.** `exclude_versions` present -> entry matches unless the version is
   ignored (exact match, or `startsWith(ver + ".")`). Otherwise `include_versions` must match
   by equality or prefix.
2. **Label gating applies to `master` only.** When the version is `master` and the trigger
   supplied a `labels_selector`, the entry is skipped unless its `labels` list contains that
   selector. **Non-master versions bypass label gating entirely** — this is why release-branch
   entries carry `labels: []`.
3. **Throttling.** `job_throttle_category` serialises jobs that would otherwise collide, in
   practice one category per (region, instance family).

## 3. The legacy path — `vars/perfRegressionParallelPipelinebyRegion.groovy`

Still present (32 KB). Holds the original `testRegionMatrix` list (defined around line 92) and
its own `parameterizedCron` block. Its header comment (lines 1-30) remains a good
human-readable summary of the matrix by label and version tier.

Label counts in the legacy matrix: `master-weekly` x8, `master-3weeks` x5, `master-monthly` x4,
`gce-custom-monthly` x2, `master-daily` x1, `alternator-weekly` x1.

When `scylla_version == "master"` it collects the unique `"{cloud_provider}-{arch}"` keys and
runs `./docker/env/hydra.sh list-images -c <provider> -r <region> -a <arch> -o json` **once per
unique combination**, caching the resolved image name. Entries flagged `rolling_upgrade_test`
or `microbenchmark` get `image_name_for_job = null` — they resolve their own images.

> New work goes in the trigger YAML, not here.

## 4. The per-job pipeline — `vars/perfRegressionParallelPipeline.groovy`

`def call(Map pipelineParams)`. Reads `backend`, `region`, `availability_zone`,
`xcloud_provider` / `xcloud_env`, `gce_datacenter`, `oci_region_name`, `azure_region_name`,
`provision_type`, `post_behavior_*`, `sub_tests` (JSON list), `test_config` (JSON list of
YAMLs), `test_name`, `k8s_*`, `base_versions`, `manager_version`.

Fans out **one parallel stage per sub-test**. Each stage is an independent SCT run with its own
cluster — so sub-tests within a job do not share state or interfere.

The `test_config` list is where the layering happens; order matters, later entries win:

```groovy
test_config: '''["test-cases/performance/perf-regression-predefined-throughput-steps.yaml",
 "configurations/performance/cassandra_stress_gradual_load_steps_enterprise.yaml",
 "configurations/performance/latency-decorator-error-thresholds-steps-ent-tablets.yaml"]''',
```

Related pipelines:

| Groovy var | Used by |
|---|---|
| `perfSearchBestConfigParallelPipeline` | `jenkins-pipelines/qa/perf-search-throughput-best-config*.jenkinsfile` (2 jobs) |
| `perfSimpleQueryOfflineInstallerTriggerArm` / `...X86` | offline-installer microbenchmark triggers |
| `triggerMatrixPipeline` | the generic YAML-driven trigger |

## 6. Region assignment

Perf jobs in the same region at the same time contend for capacity and network, which shows up
as latency noise. The assignment rules and the current allocation are in
[../perf-tests-region-scheduling.md](../perf-tests-region-scheduling.md).

Constraints:

- Weekly, 3-weekly and monthly tests must not overlap in a region.
- Release-triggered runs (unpredictable timing) **may** overlap with monthly, but **not** with
  weekly or 3-weekly — hence separate MASTER and RELEASE regions per job.
- Available regions: `us-east-1`, `us-east-2`, `us-west-2`, `eu-west-2`, `eu-west-3`,
  `eu-north-1`.

When you add a job, pick a region that is free at its cadence and record it in that document
as well as in `job_throttle_category`.
